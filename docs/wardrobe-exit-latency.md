# Android 의상룸 복귀 지연 측정

의상룸에서 나올 때마다 화면이 약 37초 멈춘 뒤 캐릭터 선택 화면으로 돌아온다는 신고를 조사했다. **v0.3.21 업데이트 후 같은 경로의 지연이 해결됐다는 사용자 확인을 받았다.** 이전의 표시 실패 후 종료 대기 수정과 구분한다. 별도의 실기기 계측이나 각 변경의 효과를 분리한 측정은 아니다.

사진으로 확인한 경로는 **홈의 着替え → 전용 캐릭터 목록 → 3D 의상 화면 → 戻る → 전용 목록**이다. 원본에서는 `HomeCostumeScreen`에서 `CharacterCostumeScreen`을 연다. 이번 판의 종료 준비·숨김·비활성화 측정은 해당 3D 화면을 포착한다.

[Android v0.3.21 다운로드](https://github.com/tagundo/IdolyPride_client/releases/tag/local-server-v0.3.21). 서버와 연결용 클라이언트가 각각 필요하다.

## 확인한 내용

- 원본의 의상 확인 요청은 현재 캐릭터의 의상·헤어만 보낸다. 전체 해금 목록을 모두 반환하지 않는다.
- 실제 전체 해금 데이터와 Android와 같은 순수 Python protobuf를 사용한 격리 호스트 측정에서, 가장 많은 캐릭터의 107개 항목 확인은 약 41ms였다. 기기 측정값은 아니며 휴대폰의 37초 원인을 확정하지 않는다.
- 변경 없는 스냅샷도 SQLite에 다시 쓰던 경로는 생략한다. 응답·읽음 처리·설정·트랜잭션은 유지한다.
- 확인한 의상룸 종료 함수에 30초·37초 고정 대기는 없었다. GC나 리소스 해제를 건너뛸 근거도 확인되지 않았다.

## v0.3.21에서 줄이는 작업

사용자 기록에서 의상 확인 RPC는 149ms였고 종료 준비 함수의 최초 동기 호출은 114ms였지만, 비활성화는 뒤로가기 약 38초 뒤에 관측됐다. 원본 API는 서버 응답을 받은 다음 사용자 데이터 변경을 반영해야 요청의 비동기 작업을 완료한다. 따라서 RPC 시간이나 최초 함수 반환 시간만으로 클라이언트의 응답 반영 비용까지 제외할 수 없다. 멀티스레드 렌더링 설정을 끈 재현에서도 사용자는 30초 이상 대기를 보고했다.

원본의 확인 요청 필터는 캐릭터 일치 여부만 검사한다. Android 연결용 클라이언트는 원본 필터를 먼저 호출하고, 일치한 항목 중 **클라이언트에서 이미 확인된 의상·헤어**만 요청에서 제외한다. 추가 확인 getter는 읽기 전용이며 원본 함수에 후킹하지 않는다. 아직 확인되지 않은 항목은 계속 전송하므로 서버 응답이 유실돼 클라이언트만 이전 상태인 경우에도 재동기화할 수 있다.

서버는 의상·헤어 ID가 모두 없는 요청에 `commonResponse` 부모만 반환한다. 빈 `updatedData`·`deletedData` 메시지도 원본의 컬렉션 갱신을 실행시키지만, 두 자식이 모두 없으면 원본은 즉시 반환한다. 비어 있지 않은 요청은 서버에서 이미 확인했더라도 요청한 현재 항목을 다시 반환한다. 확인 상태·의상 선택·응답 재시도 동작은 유지한다.

이는 확인된 중복 처리의 제거다. 사용자는 지연 해결을 확인했지만, 확인된 행의 필터링과 빈 변경 메시지 생략 중 어느 변경이 얼마나 기여했는지는 분리 측정하지 않았다. 사용자 그래픽 설정·멀티스레드 렌더링 설정·원본 종료 작업·취소 토큰은 바꾸지 않는다.

## 다른 화면의 중복 처리 검사

원본 Android 6.1.1의 읽기 전용 응답 14개에서 같은 빈 변경 메시지 생성 패턴을 확인했다. 촬영 2개, 360 LIVE 2개, Company 2개, 선물함·친구 6개, 감상 모드 스토리 목록 2개다. 구체 응답 클래스의 28개 접근자는 두 자식 메시지의 null을 그대로 전달한다. `commonResponse` 부모와 실제 목록은 유지하면서 빈 두 자식만 생략한다. 해시로 고정한 원본 응답 캡처는 변경하지 않는다.

원본 `UpdatedData` 생성자는 빈 `RepeatedField` 객체를 40개, `DeletedData` 생성자는 12개 만든다. 두 자식의 생략은 이 52개 객체의 생성과 불필요한 갱신 호출을 줄인다. 새 배열 52개를 만든다는 뜻은 아니다. 빈 컬렉션 갱신은 원래도 `OnAfterUpdate` 전에 반환하므로, 모든 알림 캐시를 재계산한다고 해석하면 안 된다. Common 부분의 전송량 차이는 8바이트에서 4바이트로 작다.

추가 서버 최적화는 다음 범위로 제한한다.

- 이름·소개가 같으면 전체 스냅샷 재직렬화를 생략하고 원본 바이트를 유지한다. 재시도에 필요한 현재 전체 행 응답과 알 수 없는 필드는 유지한다.
- 설정 바이트와 스키마가 모두 같으면 실제 DB 갱신을 생략한다. 최초 삽입·변경·스키마 교정·기존 트랜잭션은 유지한다.
- 감상 모드의 특별 스토리는 고정 마스터의 부모·에피소드 검증을 핸들러별로 재사용한다. 한 편을 읽으려고 전체 메뉴 DTO를 만들던 작업을 제거한다. 소유권·진행·일반 계정의 해금 상태는 캐시하지 않는다. 언어·마스터 변경 후 재시작하면 새 핸들러가 검증한다.
- 덱 저장은 해당 덱과 현재 배치만 전체 응답한다. 다른 덱을 다시 교체하지 않고, 생성 시 사용자 정보·덱 번호 증가와 현재 행의 재시도 ACK를 유지한다. 삭제는 정확한 삭제 행만 보내되, 원본이 요구하는 빈 `updatedData` 자식은 유지한다. 읽기 전용 응답의 빈 자식 제거를 삭제 응답에 일괄 적용하면 안 된다.

덱이 1개인 공개 테스트 프로필에서는 덱 응답 절감이 없다. 원본 상한인 30개 덱으로 구성한 가상 모델에서는 저장 응답이 180행·9,788바이트에서 6행·334바이트로 줄어든다. 사용자 프로필이나 CPU 시간 측정값은 아니다. 기존의 새 덱 번호 0 생성 재시도·유실된 슬롯 삭제 응답의 재전달 동작은 확장하지 않는다.

캐시된 파일과 Range 요청은 이미 파일 식별 정보로 검증 결과를 재사용한다. 새 다운로드의 두 번째 전체 파일 검사는 유지한다. 이를 생략한 후보는 같은 inode가 수정되고 mtime이 복원되는 동시 변경 검사에서 손상 파일을 신뢰할 수 있어 철회했다.

다른 화면의 실제 지연 감소나 MV의 FPS 개선은 계측하지 않았다. 이번 검사는 메뉴 전환·저장·응답 반영의 불필요한 작업을 대상으로 한다.

## 새로 기록하는 시간

원본 함수의 입력·반환값·예외·취소 토큰을 유지하고, 함수 진입과 반환 시점만 측정한다. 비동기 작업을 대신 완료시키거나 원본 작업을 소비하지 않는다.

의상룸과 피팅룸 뒤로가기, 닫힘 준비, 숨김, 비활성화, 캐릭터 목록 표시·복귀 콜백, 해당 복귀 관측 중의 GC·미사용 자원 해제 호출을 구분한다. 서버의 의상 확인·설정 RPC에는 처리 시간과 워커 대기 시간을 기존 로그에 덧붙인다.

일반 의상룸은 화면 버튼이 뒤로가기 함수를 우회해도 원본 종료 준비 함수에서 관측을 시작한다. 별도 피팅룸의 공통 UI 버튼 연결은 확인되지 않아 해당 경로는 기록이 누락될 수 있다. 입력이 생략될 수 있는 공유 제네릭 함수에 무리하게 관측을 붙이지 않는다.

진단 JSON의 `wardrobe_probe.client.exit`에는 현재 단계, 총 경과 시간, 원본 호출 안에 있는지, 가장 긴 동기 호출과 구간별 최장 동기 시간이 남는다. 구간은 최대 8종이며 짧은 호출이 반복돼도 긴 호출 기록을 지우지 않는다. 중첩 호출의 시간은 서로 포함될 수 있으므로 더해서 전체 시간으로 해석하지 않는다. 비동기 함수의 반환 시간은 전체 작업 완료 시간이 아니다. `completed`는 원본 복귀 콜백 반환을 관측했다는 뜻이며 화면 렌더링 완료를 보증하지 않는다.

**홈 着替え 전용 목록의 최종 복귀 시점은 현재 판에서 관측하지 못한다.** 일반 아이돌 목록의 복귀 콜백과 다르며, 홈 목록의 `_isBusy=false` 콜백은 의상 화면을 열기 시작할 때 쓰여 복귀 표지로 사용할 수 없다. 이 경로에서는 `elapsed_ms`가 실제 복귀 후에도 증가할 수 있다. `active`도 관측 창의 상태다. 이 두 값을 실제 정지 시간이나 현재 화면의 멈춤 여부로 해석하지 않고, 구간별 동기 처리 시간과 서버 RPC 시간을 먼저 확인한다.

2분은 관측 창의 길이이며 게임 작업에 시간 제한을 추가하지 않는다. 기존 렌더 모드 관측의 `sample_age_ms`도 함께 보관한다. 포인터·계정·의상 ID·인증 정보는 이 시간 기록에 넣지 않는다. 기존 schema1 진단도 계속 받는다.

## 재현 순서

1. Android 서버와 연결용 클라이언트를 각각 업데이트한다. 앱 삭제·데이터 지우기는 하지 않는다.
2. 게임을 완전히 종료했다가 서버의 **진단 게임 실행**으로 연다.
3. 의상룸에 들어갔다가 뒤로가기를 누르고, 캐릭터 선택 화면이 돌아올 때까지 게임을 전면에 둔다. 기다리는 동안 다른 앱으로 전환하면 그 시간이 관측에 포함될 수 있다.
4. 복귀한 뒤 서버 앱의 **진단 기록 내보내기**를 사용한다. 서버 로그에는 의상룸 복귀 단계·경과·최장 동기 시간이 표시된다.

이 기록으로 서버 응답을 기다리는지, 특정 원본 함수가 오래 실행되는지, 함수 밖에서 비동기 전환이 대기하는지를 구분한다. 실제 기기의 원인과 지연 감소는 이 재현 기록으로 추가 확인해야 한다.
