# Android 의상룸 복귀 지연 측정

의상룸에서 나올 때마다 화면이 약 37초 멈춘 뒤 캐릭터 선택 화면으로 돌아온다는 신고를 조사한다. 이전의 표시 실패 후 종료 대기 수정과 구분한다. 이번 판이 37초 지연을 해결했다고 주장하지 않는다.

## 확인한 내용

- 원본의 의상 확인 요청은 현재 캐릭터의 의상·헤어만 보낸다. 전체 해금 목록을 모두 반환하지 않는다.
- 실제 전체 해금 데이터와 Android와 같은 순수 Python protobuf를 사용한 격리 호스트 측정에서, 가장 많은 캐릭터의 107개 항목 확인은 약 41ms였다. 기기 측정값은 아니며 휴대폰의 37초 원인을 확정하지 않는다.
- 변경 없는 스냅샷도 SQLite에 다시 쓰던 경로는 생략한다. 응답·읽음 처리·설정·트랜잭션은 유지한다.
- 확인한 의상룸 종료 함수에 30초·37초 고정 대기는 없었다. GC나 리소스 해제를 건너뛸 근거도 확인되지 않았다.

## 새로 기록하는 시간

원본 함수의 입력·반환값·예외·취소 토큰을 유지하고, 함수 진입과 반환 시점만 측정한다. 비동기 작업을 대신 완료시키거나 원본 작업을 소비하지 않는다.

의상룸과 피팅룸 뒤로가기, 닫힘 준비, 숨김, 비활성화, 캐릭터 목록 표시·복귀 콜백, 해당 복귀 관측 중의 GC·미사용 자원 해제 호출을 구분한다. 서버의 의상 확인·설정 RPC에는 처리 시간과 워커 대기 시간을 기존 로그에 덧붙인다.

일반 의상룸은 화면 버튼이 뒤로가기 함수를 우회해도 원본 종료 준비 함수에서 관측을 시작한다. 별도 피팅룸의 공통 UI 버튼 연결은 확인되지 않아 해당 경로는 기록이 누락될 수 있다. 입력이 생략될 수 있는 공유 제네릭 함수에 무리하게 관측을 붙이지 않는다.

진단 JSON의 `wardrobe_probe.client.exit`에는 현재 단계, 총 경과 시간, 원본 호출 안에 있는지, 가장 긴 동기 호출과 구간별 최장 동기 시간이 남는다. 구간은 최대 8종이며 짧은 호출이 반복돼도 긴 호출 기록을 지우지 않는다. 중첩 호출의 시간은 서로 포함될 수 있으므로 더해서 전체 시간으로 해석하지 않는다. 비동기 함수의 반환 시간은 전체 작업 완료 시간이 아니다. `completed`는 원본 복귀 콜백 반환을 관측했다는 뜻이며 화면 렌더링 완료를 보증하지 않는다.

2분은 관측 창의 길이이며 게임 작업에 시간 제한을 추가하지 않는다. 기존 렌더 모드 관측의 `sample_age_ms`도 함께 보관한다. 포인터·계정·의상 ID·인증 정보는 이 시간 기록에 넣지 않는다. 기존 schema1 진단도 계속 받는다.

## 재현 순서

1. Android 서버와 연결용 클라이언트를 각각 업데이트한다. 앱 삭제·데이터 지우기는 하지 않는다.
2. 게임을 완전히 종료했다가 서버의 **진단 게임 실행**으로 연다.
3. 의상룸에 들어갔다가 뒤로가기를 누르고, 캐릭터 선택 화면이 돌아올 때까지 게임을 전면에 둔다. 기다리는 동안 다른 앱으로 전환하면 그 시간이 관측에 포함될 수 있다.
4. 복귀한 뒤 서버 앱의 **진단 기록 내보내기**를 사용한다. 서버 로그에는 의상룸 복귀 단계·경과·최장 동기 시간이 표시된다.

이 기록으로 서버 응답을 기다리는지, 특정 원본 함수가 오래 실행되는지, 함수 밖에서 비동기 전환이 대기하는지를 구분한다. 실제 기기의 원인과 지연 감소는 이 재현 기록으로 추가 확인해야 한다.
