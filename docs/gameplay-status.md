# 로컬 게임 상태 구현 범위

v0.3.1 베타는 자동 편성 뒤 `Deck.Save`의 `ManualAuto(3)`·`QuestAuto(4)` 저장이 `UNIMPLEMENTED`로 실패하던 문제를 수정했습니다. 실제 ARM64 Android 서버 APK에서 이전 오류·업데이트·저장·재시작을 검사했으며 실제 게임의 자동 편성 버튼 동작은 아직 확인하지 않았습니다. 설치 파일과 범위별 검사 기록은 [v0.3.1 릴리스](https://github.com/tagundo/IdolyPride_client/releases/tag/local-server-v0.3.1)에 있습니다. 저장소 접근 권한과 GitHub 로그인이 필요합니다. 원본 APK와 일반 연결판의 실행 결과 및 전체 미구현 목록은 [원본 기준 분석](original-client-baseline.md)을 따릅니다.

v0.3.0 베타에서 추가한 프로필 조회·이름 변경·소개문과 선호 캐릭터 저장, 카드 레벨 도달 미션 한 개의 진행·조회는 유지합니다. 이 기능들의 자동 검사와 실제 ARM64 Android 서버 APK의 암호화 API·기존 데이터 보완·업데이트·재시작 검사, Mac 앱 실행 검사 기록은 v0.3.0 범위이며 새 기능의 실제 게임 화면은 아직 확인하지 않았습니다.

상태 핸들러는 6.1.1 스키마와 같은 버전의 마스터를 사용합니다. Android 사용자 기기에서 홈·캐릭터·편성과 초기 튜토리얼 전체 진행을 확인했습니다. v0.2.12의 레슨 보상·초기 카드 강화·새 유닛 생성·메시지 확인 이후 타이틀을 거쳐 홈으로 재접속한 기록도 확인했습니다. 일반 라이브의 실제 게임 재생·결과 화면 검증은 남아 있습니다. 기본값이 꺼진 v0.3.0 베타의 제한된 계산·정산은 [첫 메인 라이브 실험 기능](first-live-support.md)에서 별도로 설명합니다.

## 일반 레슨 보상과 실게임 검사

튜토리얼 완료 후 실제 기기에서 다음 중단 요청은 `Activity.ReceiveLessonReward`였습니다. v0.2.13은 초기 메인 지역 `area-main-001`의 일반 레슨을 지원합니다. `Home.Enter`의 기존 필드와 `lessonInfo.lessonProgress`, 실제 수령 응답이 같은 영속 시간 기록을 사용합니다. User snapshot에 없는 시간 기록은 별도 프로필별 테이블에 저장하며 자원 지급과 같은 SQLite 트랜잭션에서 갱신합니다.

공개 공식 홈 응답 네 개에서 확인한 기본 비율은 10초당 골드5·매니저 경험치8·레슨 피스3, 보관 한도는 12시간입니다. 이 **기본 비율만 적용하는 로컬 정책**을 사용합니다. 공식 신규 계정의 추가 경험치 배율 조건은 아직 확인되지 않았으며 캠페인·레벨어시스트Pt·즉시 촉진·다른 지역의 비율은 구현하지 않았습니다. 수량·보관 한도와 원본 해시는 `tests/fixtures/official-initial-lesson-rates.v1.json`에 기록했습니다.

Android 설치 앱과 Mac 묶음 엔진 모두 실제 10초 경과 후 기본 수량 수령·즉시 재요청의 추가 지급 방지·재시작 후 시간과 재화 보존을 검사했습니다. 계정 식별자·세션·설정·관련 없는 snapshot 필드도 유지합니다. [앱 검사 기록](https://github.com/tagundo/IdolyPride_client/actions/runs/42758720464)은 실제 게임 메뉴 탐색과 별도의 검증입니다.

튜토리얼 중에는 저장 없는 미리보기만 반환합니다. 완료 후 최초 접근 시 현재부터 누적하며 기존 로그인 시각이나 가져온 계정의 과거 시간을 소급 지급하지 않습니다. 완성된 10초 구간을 지급하고 나머지 시간은 보존합니다. 12시간 초과분은 수령 시 폐기해 반복 수령으로 상한을 우회하지 못하게 합니다. 시계가 뒤로 가면 음수 보상을 만들거나 수령 시각을 뒤로 옮기지 않습니다. 계정 snapshot을 명시적으로 가져오면 해당 계정의 로컬 레슨 시간은 함께 초기화합니다.

이전 진단판 수동 Actions 작업은 현재 기본 비활성화했습니다. 이 작업은 API35 ARM 변환 에뮬레이터와 Lavapipe에서 서버·실제 6.1.1 진단 게임을 함께 실행했습니다. 새 검증은 원본 APK → 일반 연결판 → 필요한 진단 순서이며 [원본 기준 분석](original-client-baseline.md)에 기록합니다. 같은 AVD에서 CPU 명령·GLES uniform 배열 링크·루트 지원을 먼저 확인합니다. 검증 전용 APK에는 소프트웨어 AES·스토어 없는 초기화·GLES3 설정을 사용하며 공개 게임 APK는 바꾸지 않습니다. 초기 튜토리얼 완료 프로필은 알려진 로컬 RPC로만 준비하고, 이 준비 과정과 실제 게임에서 발생한 요청을 구분해 기록합니다. UI 트리·화면·예외·서버 요청을 자료로 남기며 실행 성공을 홈이나 메뉴 성공으로 취급하지 않습니다.

최신 실제 게임 검사 [42810660579](https://github.com/tagundo/IdolyPride_client/actions/runs/42810660579)은 같은 API35·Lavapipe 환경의 축소 화면에서 Android 전체화면 안내·다운로드·공지를 지나, 가리지 않은 홈 배경과 중앙 3D 캐릭터를 확인했습니다. 실제 레슨 입력으로 `Activity.ReceiveLessonReward → OK`, `Home.Enter → OK`가 발생했고 골드60·매니저 경험치96·레슨 피스36 수령과 매니저2→3 안내가 표시됐습니다. 그 안내 아래의 보상 창 닫기는 비활성 상태였으므로 탐색기는 조기에 중단했습니다. 메뉴 결과는 0개이며 나머지 메뉴와 일반 라이브 재생을 확인한 실행은 아닙니다. 게임 PID는 유지됐고 새 관리 예외·`SIGILL`·GLSL 링크 오류도 관측하지 못했습니다. 앞선 공지 뒤에서 발생한 메뉴 입력은 계속 검증에서 제외합니다.

실행과 결과 파일은 [실제 게임 자동 점검](actual-game-qa.md)에 정리했습니다.

튜토리얼 완료 도중 일부 손가락 안내가 뒤로가기 이외의 위치를 가리킨 것 같다는 사용자 보고도 있습니다. 진행 중단은 없었으며 표시 위치 문제의 정확한 재현은 남아 있습니다.

## 제목 화면의 환불 기간 조회

`Refund.GetTerm`은 `System.Check` 다음, `Auth.Login` 전에 호출되는 익명 조회입니다. v0.2.1은 로그인 없이 `startDatetime=endDatetime=4102444800000`(2100-01-01 UTC), `shopInvalidStartDatetime=0`을 반환합니다. 공식 환불 신청·잔액 조회는 실행하지 않습니다.

6.1.1의 `TitleView.StartAnimationAsync` 상태 머신(`0x5173d0c`)은 시작·종료 값 0을 무제한 기간으로 취급하므로 둘 다 0으로 두면 환불 버튼이 나타납니다. 미래 시작·종료를 사용해 환불 화면을 비활성화합니다. `CheckOpenStoneShop`(`0x528d338`)은 `IsBefore(shopInvalidStartDatetime)`을 사용하므로 0은 유료 상점 진입을 닫습니다. `GetPaidStone`과 사용자 데이터에는 기존 인증 검사를 유지합니다.

실제 Android에서 관측한 `System.Check → Refund.GetTerm`을 재현한 뒤 `Auth.Login`으로 이어지는 흐름을 HTTP/2·grpcio와 에뮬레이터 검사에 포함하며, 이 조회가 기존 프로필·세션을 바꾸지 않는지 검증합니다.

선호 캐릭터 설정은 원본 6.1.1 `ProfileTopScreenPresenter.UpdateFavoriteCharaAsync` 상태 머신의 네트워크 호출(`0x433b1ec`)과 `Profile.UpdateFavoriteCharactersAsync` 요청 생성(`0x474c014`, 반복 ID 복사 `0x474c09c`–`0x474c0bc`)을 대조했습니다. 중복 금지·현재 보유 검증은 로컬 정책입니다. 근거 없는 고정 인원 제한은 적용하지 않으며 선택은 현재 보유한 마스터 유효 캐릭터 수로 한정됩니다. 기존 로컬 starter가 저장하는 5명도 그대로 저장·재정렬할 수 있습니다. 목록 순서는 보존하고 빈 목록은 기존 선택을 해제합니다. 기존 user/profile이 없는 snapshot은 생성하지 않으며, 비어 있지 않은 선택은 `Character` 마스터와 해당 프로필의 보유 목록이 있어야 합니다. 이름·소개문·의상·재화·미션·설정·세션은 바꾸지 않습니다. 정확한 같은 요청의 재시도는 원래 snapshot 바이트를 유지합니다. 자동 검증은 실제 프로필 UI 확인과 구분합니다.

`Deck.Save`는 배치 1~5와 중복 참조·장비 수량·슬롯·캐릭터 제한을 검증합니다. Android의 새 덱은 번호 0을 보내며, 서버는 `deckSequence`와 기존 번호보다 큰 번호를 트랜잭션 안에서 할당하고 `Setting.deckCountMax`를 지킵니다. 번호 0 재요청에는 멱등 키가 없으므로 별도 덱을 생성합니다. `deckEditType`은 `Manual(1)`, `Auto(2)`, `ManualAuto(3)`, `QuestAuto(4)`를 지원하며 클라이언트가 선택해 보낸 배치를 저장합니다. `Unknown(0)`·알 수 없는 모드와 대여 버디 요청은 상태를 바꾸지 않고 `UNIMPLEMENTED`로 거절합니다. 버디 대여·캐릭터 그룹 제한 장비·서버의 자동 편성 계산은 아직 미구현입니다.

## 자동 편성 저장 수정: v0.3.1

이전 서버는 편집 모드 1·2만 받아 자동 편성 결과를 담은 3·4 요청도 `UNIMPLEMENTED`로 거절했습니다. v0.3.1은 같은 소유권·슬롯·장비 검사와 트랜잭션을 네 모드에 적용합니다. 카드 순서·일부 슬롯 비우기·새 덱 생성·기존 덱 변경을 저장하며 서버가 최적 편성을 새로 계산하지는 않습니다. 원본 6.1.1 Android의 `QuestAuto(4)` 요청 생성 경로를 대조했으며 `ManualAuto(3)`의 정확한 UI 호출 위치는 아직 확인하지 않았습니다.

실제 ARM64 Cuttlefish에서 v0.3.0 서버 APK의 모드 3·4 오류를 재현한 뒤, 앱 데이터를 지우지 않고 v0.3.1로 업데이트했습니다. 암호화 RPC로 네 모드의 저장과 모드 3·4의 새 번호 할당, 슬롯 제거를 검사했습니다. 잘못된 참조·버디 요청 거절과 기존 세션·덱 외 상태 보존, 서버 재시작 후 저장값도 확인했습니다. 소스의 전체 검사와 Mac 묶음 엔진·창 표시·서버 시작·종료도 통과했습니다. [v0.3.1의 Android QA 기록](https://github.com/tagundo/IdolyPride_client/releases/download/local-server-v0.3.1/IdolyPride-Local-Server-Android-QA.zip)에 범위와 결과를 담았습니다. 실제 게임의 자동 편성 버튼·저장 후 화면 검증은 남아 있습니다. 데이터 ZIP·40개 테이블·202개 원본 팩·보상 규칙은 v0.3.0과 같습니다.

## 카드 레벨 도달 미션: v0.3.0 베타

지원하는 행은 `ms-normal-card_level_achievement` 하나입니다. 원본 `Mission` 마스터의 Normal(3)·CardLevelAchievement(13)·빈 해금/이벤트 조건과 첫 임계값 5를 검증합니다. 공개 신규 계정의 `User.Get`은 진행도 1, `Card.Enhance`는 카드 2레벨과 진행도 2를 함께 반환합니다. 별도 기록의 카드·미션 `41→42`도 일치합니다. 원본 UI는 응답에 실제 포함된 미션만 열거하며 각 현재 임계값은 마스터에 정확히 존재해야 합니다. [정제한 근거](../tests/fixtures/official-card-level-mission.v1.json)에 경로·해시·원본 소비 코드의 검증 범위를 보존했습니다.

마스터를 가진 새 로컬 starter는 origin 5와 진행도 1의 한 행을 준비합니다. 기존 계정은 명시적인 origin 4만 원자적으로 5로 이행하며, 이미 있는 유효 행의 임계값·수령 상태·미지 필드는 그대로 유지합니다. 가져온 계정·출처가 없는 snapshot의 누락 행을 새로 만들지 않습니다. 가져온 계정에도 유효한 기존 행이 있으면 실제 강화에 따라 진행시킬 수 있습니다.

실제 `Card.Enhance`가 보유 카드 최고 레벨을 높일 때만 저장된 최고 도달 기록과 시각을 갱신하고 `commonResponse.updatedData.missions`로 반환합니다. 카드·소비 아이템과 같은 SQLite 트랜잭션을 사용하므로 검증 실패는 전체를 되돌립니다. 더 낮은 카드의 강화, 같은 목표 재시도, 최고 도달 기록보다 낮은 현재 보유 레벨은 미션을 증가시키거나 시각을 바꾸지 않습니다. 레벨 어시스트나 baseLevel을 진행도로 대신 사용하지 않습니다. 임계값을 넘겨도 현재 임계값은 이동하지 않습니다. `Progress(1)→Clear(2)`는 로컬 준비 완료 정책이며 공식 서버의 경계 응답과 같다고 주장하지 않습니다. 기존 `Clear/NotReceived/Received` 상태는 보존합니다.

`Mission.List`는 검증된 저장 행 하나만 읽기 전용으로 반환합니다. 전체 7,087개 마스터 행을 소유 상태로 만들거나, 누락 상태를 빈 성공 응답으로 숨기지 않습니다. 마스터·저장 행이 없거나 현재 임계값·스키마 지문이 맞지 않으면 `FAILED_PRECONDITION`입니다. `Mission.Receive`·다음 단계 수령·일일/주간 초기화·프로필 설정 미션·보상은 구현하지 않았습니다.

새 payload는 원본 암호화 팩 202개를 그대로 두고 서버용 JSON에 `Mission`을 추가해 40개 테이블을 준비합니다. 이전 payload에 이 테이블이 없으면 origin 4와 기존 홈·강화 동작을 유지합니다. 새 기능은 원본 6.1.1과 독립적인 최소 스키마, 재시도·동시 강화·재시작·가져온 상태·트랜잭션 실패·이전 payload로 자동 검증했으며 기기 UI 확인과는 구분합니다.

## 라이브 이후의 초기 튜토리얼

공개 공식 응답 00030~00057과 6.1.1 네이티브 호출 순서를 대조했습니다. 실제 클라이언트는 `Progress100 → ReceiveLessonReward → Progress120 → Card.Enhance → Progress130 → Deck.Save(number=0, type=2) → 메시지 목록/타임라인/선택 저장 → Progress140 → Message.Finish → Progress150` 순으로 요청합니다. 강화·편성·메시지 동작 전에 다음 체크포인트가 저장되는 점을 반영했습니다. 마지막 단계의 알림 권한 요청은 Android 로컬 동작입니다.

레슨 보상은 `Setting`의 10분 × 분당 수량으로 골드 1,000·매니저 경험치 50·레슨 피스 1,000을 더합니다. 매니저 레벨은 `ManagerLevel` 누적 경험치에서 계산합니다. 보상과 100→110 기록을 같은 트랜잭션에 저장해 병렬 요청·재시도에서 중복 지급하지 않습니다. 이미110 이상이면 현재 상태를 반환하며 다시 지급하지 않습니다. 캡처의 절대 잔액·매니저 정보·미션 상태는 복사하지 않습니다.

강화는 `CardLevel`의 누적 경험치 차이와 `Consumption`의 실제 레슨 피스 소비를 사용합니다. 초기 형태의 미지원·미진화·미승급 카드에서 다음 스킬 해금 경계 전까지 지원하며 매니저 레벨 상한도 적용합니다. 현재 마스터에서 매니저2레벨은 카드12레벨까지입니다. 네이티브의 두 단계 내림 계산을 사용하며 코토노1→2레벨은 피스40개, 능력치132/105/92/937로 공식 응답과 일치합니다. 잠긴 스킬 ID는 비워 둡니다. 고급 승급·진화·레벨 어시스트 계산은 별도 미구현입니다.

메시지는 `Setting.tutorialMessageId`와 실제 `Message`·`MessageGroup`의 대화·선택지를 사용합니다. 130단계 이후 로컬 도착 시각을 한 번 저장하고 해당 프로필에 안정적인 타임라인 번호를 부여합니다. `Save`는 실제 경로의 선택지만 저장하고 `Finish`는 같은 도착 기록을 유지한 채 완료·스케줄 제거를 기록합니다. 이 메시지는 신뢰도 보상이 없습니다. 일반 메시지 이벤트·전화·보상·새 메시지 생성은 구현 범위 밖입니다. 완료 단계150은 클라이언트가 명시적으로 요청해야 하며 서버가 자동 건너뛰지 않습니다.

출처는 [공개 응답 기록](https://github.com/Project-Hoshimi/sumire-sr-data/tree/c40ea107b9cc8e53ae1705f82a5c39cc9fe3be02/captures/2026-10-25_fresh_official/raw)입니다. 응답 스키마·수량·순서만 구현 근거로 쓰며 사용자 이름·타임라인 번호·시각·절대 계정 상태를 묶음에 넣지 않습니다. Android 설치 앱과 Mac 엔진 검사는 실제 암호화 RPC로100~150단계를 실행하고 재시도·재시작 후 상태와 기존 세션을 검사합니다. 이 검사는 실제 게임 화면의 최종 튜토리얼 완료 확인과 구분합니다.

메인 라이브 목록은 `AreaGroup`·`Area`·`Quest`의 실제 참조와 순서를 검증합니다. 현재 묶음에는 메인 5그룹·125지역·939퀘스트가 있습니다. 신규 프로필은 첫 지역·첫 퀘스트만 플레이 가능으로 표시하며 이후 진행은 저장된 지역 클리어 수와 개별 퀘스트 기록을 사용합니다. 목록 조회가 클리어·점수·재화·티켓·튜토리얼을 변경하지 않습니다. 해석하지 못한 해금 조건은 잠긴 상태로 둡니다. `Quest.Top`이 반드시 읽는 PvP 컨테이너와 유효한 하이어라키 등급은 제공하지만, 경쟁 시즌·상대·보상은 만들지 않습니다. 일반 퀘스트의 전투 시작과 결과 계산은 아직 구현하지 않았습니다.

v0.2.8은 `Quest.Top`의 `contestArea`도 실제 하이스코어 지역·23개 퀘스트와 저장된 기록으로 제공합니다. 콜백에서 null을 저장할 수 있더라도 이후 `LiveTopScreenPresenter.RequestLiveProgressAsync`(`0x5759ce8`~`0x5759cf4`)가 이를 반드시 읽으므로 필드 부재는 유효한 비활성 응답이 아닙니다. v0.2.7의 사용자 기기에서 `Quest.Top → OK` 직후 발생한 null 참조와 이 분기를 확인했습니다. 하이스코어 지역·퀘스트는 잠긴 상태이며 경쟁전·보상·캠페인은 생성하지 않습니다.

GameStart가 미완료(기록 없음 또는 완료 단계 150 미만)이면 실제 튜토리얼 그룹 1개·지역 1개·full/short 퀘스트 2개도 목록에 포함합니다. 두 퀘스트는 대체 선택지이며 메인 지역 클리어 순서에 묶지 않습니다. 이때 전체 그룹 목록은 6그룹·126지역·941퀘스트입니다. 완료 계정에는 기본 메인 5그룹만 반환합니다. 이 조회는 튜토리얼을 진행하거나 완료시키지 않습니다.

해당 변경 응답은 `commonResponse.updatedData`에 반영됩니다. 일반 게임 동작은 활성 로컬 세션을 유지하며, snapshot과 설정을 SQLite의 단일 트랜잭션에서 갱신합니다. 동시 요청의 변경 유실, 잘못된 요청의 부분 저장, 스키마가 다른 snapshot 수정은 거부합니다. protobuf의 알 수 없는 필드도 정상 수정 뒤 유지합니다.

`Home.Enter`는 `HierarchyDetailGrade`·`HierarchyGrade`의 실제 참조를 검증합니다. 현재 점수에서 전역 순위가 필요 없는 등급을 선택하며 순위·보상을 생성하지 않습니다. 신규 프로필의 0점 기본 등급은 현재 마스터의 `hie-007-003`입니다. 기존 snapshot의 빈 하이어라키에는 응답에서만 기본 등급을 적용하며 저장된 계정 상태는 변경하지 않습니다. 잘못된 마스터 참조는 명시적으로 거부합니다. Android 6.1.1 `HomeTop.SetHomeEnterData`(`0x566c15c`)는 현재 등급을 무조건 읽고, 조회 실패 시 `0x566c1c8`에서 null 참조로 중단합니다.

`Home.Enter`의 이벤트·활동·배너 컨테이너는 로컬 콘텐츠가 없다는 구조를 반환합니다. 급여·자동 보상·진행 중인 활동 결과를 만들어내지는 않습니다. 메인 지역 선택에는 `Area` 마스터가 필요하며 다른 지역 유형을 임의로 메인 지역으로 취급하지 않습니다.

진행 중인 특별 홈 이벤트가 없으면 `homeFishHeavenInfo` 메시지는 보내지 않습니다. Android 6.1.1의 `HomeTop.ShouldHideLoading`(`0x566c9b0`)과 홈 전환(`0x5675ff4`~`0x5676008`)은 이 메시지가 null인지 검사합니다. 빈 메시지도 존재하면 일반 로딩 화면을 숨기지 않으므로, v0.2.6은 이 선택 필드를 응답에서 제외합니다. v0.2.5와 진단판 v0.2.1의 실제 기기 기록에서 배경·캐릭터·홈 표시 전환은 통과하고 `loading_hide`만 누락된 것을 확인했습니다. 이 변경은 응답만 수정하며 저장된 계정·튜토리얼·세션을 변경하지 않습니다.

## 라이브 리소스 준비

v0.2.9의 사용자 기기에서 초기 카드 보완과 5인 편성·시작 버튼 표시를 확인한 뒤, 다음 요청인 `Quest.ListAsset`이 `UNIMPLEMENTED`로 중단됐습니다. v0.2.10은 이 읽기 전용 API를 구현합니다. v0.2.11은 그다음 `Tutorial.StartQuest`의 원본 기록 재생도 제공합니다. 일반 `Quest.Start` 계산·보상은 별도 미구현 기능입니다.

일반 퀘스트의 응답은 저장된 덱의 자리 1~5에 해당하는 `LiveCharacterAssetInfo`의 `characterId`, `costumeId`, `hairId`만 포함합니다. 직접 선택한 외형과 비어 있는 설정의 라이브·기본 외형을 실제 마스터와 보유 관계에 따라 해석합니다. 클라이언트는 이 ID로 모델을 조회하고 무대·음악 등은 퀘스트의 원본 마스터를 통해 준비합니다. 리소스 경로는 기존 Octo 경로를 사용합니다.

원본 호출부는 일반 덱 이름도 `buddyDeckName`에 넣으므로 이 문자열만으로 대여 기능으로 취급하지 않습니다. 실제 버디 배치가 있는 요청은 아직 `UNIMPLEMENTED`입니다. 목록 조회는 snapshot·덱·설정·세션·튜토리얼·재화·라이브 기록을 변경하지 않습니다.

## 원본 튜토리얼 기록 재생

v0.2.10 사용자 기기에서 `Quest.ListAsset → Deck.Save`는 정상 통과하고 `Tutorial.StartQuest`에서 미구현으로 중단되는 것을 확인했습니다. v0.2.11은 [공개된 공식 응답 기록](https://github.com/Project-Hoshimi/sumire-sr-data/tree/c40ea107b9cc8e53ae1705f82a5c39cc9fe3be02/captures/2026-10-25_fresh_official/raw)의 short/full 두 개를 검증해 재생합니다. 임의의 승리나 점수, 일반 전투 계산을 생성하지 않습니다.

기록의 고정 편성은 사쿠라·나기사·코토노·치사·레이의 레벨 1 기본 카드입니다. 추가 출연자는 short의 메이와 full의 시즈쿠입니다. 선택한 덱으로 새 전투를 계산하지 않으며 저장된 덱은 유지합니다. 튜토리얼 리소스 목록은 선택 덱 뒤에 시연 편성과 추가 출연자의 외형을 중복 없이 보탭니다. 기존 기본 덱에서는 short 8개·full 9개 외형, 일반 퀘스트는 기존 5개입니다.

원본 short는 158개 차트·8,813점, full은 156개 차트·10,717점입니다. 현재 6.1.1 스키마의 알려진 필드·enum, 마스터의 차트 순서·카드 능력치·스킬 참조·외형과 점수 합계가 일치하는 것을 확인했습니다. 시연 데이터의 카드·스킬·숫자 인덱스·타임라인·점수·랭크 기준은 유지합니다.

패키징 전에 캡처의 사용자 ID·이름·상세 로그 ID를 제거하고 빈 `CommonResponse`로 새 응답을 만듭니다. 실행할 때 단일 시연 사용자의 ID를 로컬 `UserPublic.publicUserId`로, 표시 이름을 현재 매니저 이름으로 연결합니다. 원본 `CreateUserDeck`(`0x489bbb4`)은 서버 ID가 아닌 public ID를 비교합니다. 상세 로그는 연결하지 않으며 `isDisplayDetailAvailable=false`로 미구현 분석 버튼을 비활성화합니다.

`Tutorial.StartQuest`와 리소스 목록 요청은 계정·카드·덱·재화·세션·설정·튜토리얼·라이브 기록을 변경하지 않습니다. 재생 뒤 클라이언트가 별도로 요청하는 `Tutorial.Progress`는 기존 진행 핸들러에서 처리합니다. 이 튜토리얼 재생 경로는 일반 라이브 결과를 계산하지 않습니다. 출처와 고정 해시·개인정보 제거 범위는 [튜토리얼 재생 데이터](tutorial-replay-data.md)에 기록합니다.

## 신규 프로필의 시작 데이터

`seed_starter_profile(state, schema, profile, master_dir)`는 snapshot이 없는 프로필에서만 사용합니다. 기존 공식 계정 snapshot이나 이미 생성한 로컬 프로필에는 자동 적용하지 않습니다.

시작 캐릭터는 `Character.type=1`이며 `viewConditionId`·`unlockConditionId`가 모두 빈 일반 캐릭터 17명입니다. Android 6.1.1의 `GetSubCharacterCandidate`는 보유 목록을 검사하지 않고 이 마스터 풀에서 홈 배경 인물을 선택합니다. 이어 `CreateActorDescriptor`는 `UserCharacter.FindById` 결과를 무조건 읽으므로 5명만 준비하면 나머지 12명 선택 시 null 참조가 발생할 수 있습니다. 조건이 있는 `char-kan/kor/mhk` 등은 제외합니다. 이 17명은 실제 `initial_user_reward`의 캐릭터 목록과도 일치합니다.

`Setting.tutorialPhotoShootingCharacterIds`의 5명은 기본 즐겨찾기·홈 배치에 사용합니다. 각 캐릭터의 기본·라이브 의상과 헤어 소유 관계·착용 가능성을 실제 마스터로 검증합니다. 활동 레벨 1 체력은 `CharacterActivityLevel`에서 가져오며 최초 메인 지역의 퀘스트 참조도 검증합니다.

현재 신규 데이터에는 레벨 1 매니저, 위 캐릭터·외형, 홈 배치와 GameStart step 0이 포함됩니다. v0.2.9는 원본 `Reward.initial_user_reward`에 정의된 초기 카드 17개·촬영 아이템 1개·레슨 피스 100개를 함께 준비합니다. 초기 지급을 처리한 공식 RPC와 시점은 확인하지 못했으므로 이 부분은 마스터에 근거한 로컬 계정 생성 정책입니다. `initial_user_gift`, 프리미엄 재화·클리어 보상·튜토리얼 완료·기능 전체 해금은 적용하지 않습니다. 마스터 참조 검증이 실패하면 부분 프로필이나 snapshot을 남기지 않습니다.

초기 카드는 레벨 1·마스터의 초기 레어도와 기본 능력치를 갖습니다. 수치는 원본 `CalcCardParameter`(`0x46a4b7c`)의 두 번 내림 계산을 따르며, `CardLevelRelease`의 레벨 1 해금만 현재·기본 스킬과 포토 슬롯에 반영합니다. 예를 들어 초기 코토노는 보컬 93·댄스 74·비주얼 64·스태미나 935이며 첫 스킬과 포토 2칸만 해금됩니다. 아직 배우지 않은 스킬은 ID도 비워야 합니다. 클라이언트는 스킬 레벨 0이어도 유효한 ID가 있으면 배운 스킬로 판단합니다.

기본 덱은 `Setting.tutorialPhotoShootingCharacterIds`의 5명에 해당하는 보유 초기 카드와 라이브 의상·헤어로 편성합니다. 이는 로컬 기본 편성이며 공식 튜토리얼의 고정 편성이라고 주장하지 않습니다. Android 원본 `DeckBase.get_IsPlayable`(`0x51f02a0`)은 다섯 자리의 `UserCard`가 모두 있는지 검사하고, 하나라도 없으면 `SetDeck`과 `FabStateModel.Toggle(false)`를 통해 라이브 시작 버튼을 숨깁니다. v0.2.8 사용자 화면에서는 라이브 메뉴는 열렸지만 빈 기본 덱 때문에 안내 손가락이 빈 버튼 위치를 가리켰습니다. 이 편성 보완은 실제 전투 시작·결과 계산 구현과 별개입니다.

`repair_starter_roster`는 출처 표시가 있는 구형 로컬 프로필 또는 이전 서버의 5명·기본 외형·빈 `Local deck`·고정 홈 배치·식별자가 일치하는 구성을 보완합니다. 출처 없는 데이터에 다른 인벤토리·잔액이 있으면 보정하지 않습니다. 가져오기는 출처 0으로 표시하여 제외하며, 로스터 보완은 출처 버전을 2까지 갱신합니다. 누락 캐릭터 추가와 버전 갱신은 한 SQLite 트랜잭션으로 수행합니다. 기존 캐릭터·외형·진행·이름·설정·세션·알 수 없는 protobuf 필드는 유지합니다.

v0.2.7의 기본 배치 보정은 버전 3이며 홈·트레이닝·활동·아이돌 4곳에 서로 다른 보유 캐릭터를 지정합니다. 같은 캐릭터·외형의 로딩 작업은 같은 3D 객체를 캐시에서 공유하므로, 비활성 화면의 늦은 작업이 활성 홈 객체의 위치와 표시 참조를 바꿀 수 있습니다. 원본 코드의 실행으로 이 간섭과 서로 다른 캐릭터를 사용하는 경우의 분리를 확인했고, 업데이트 후 사용자 기기에서 중앙 모델 표시가 복구된 것을 확인했습니다.

`repair_starter_home_positions`는 버전 2의 정확한 구형 기본 구성(4곳 모두 첫 기본 캐릭터·랜덤 배치 없음)만 버전 3으로 보완합니다. 기본 홈 1번의 캐릭터는 유지하고 나머지 3곳의 캐릭터만 분리합니다. 로스터 보완 다음에 실행하므로 구형 5명 프로필도 순서대로 갱신됩니다. 가져온 계정이나 기본 구성으로 인식되지 않는 배치, 직접 바꾼 배치·랜덤 배치는 건드리지 않으며 세션·설정·튜토리얼·기타 protobuf 필드를 보존합니다.

v0.2.9의 `repair_starter_inventory`는 버전 3으로 표시된 로컬 기본 계정 중 레벨 1·빈 `Local deck` 하나·카드/아이템/편성 없음·저장된 GameStart 단계 0 또는 10·라이브 기록 없음인 경우에만 초기 지급과 5인 편성을 한 번 보완하고 버전 4로 갱신합니다. 가져온 계정·사용자 인벤토리나 덱·진행된 계정은 제외합니다. 캐릭터·홈·이름·설정·세션·튜토리얼과 알 수 없는 protobuf 필드를 유지하며, 새 지급과 출처 버전은 같은 SQLite 트랜잭션에서 저장합니다.

사용하는 마스터 파일은 `tools/build_server_payload.py`의 `TABLES`에 명시한 정규 테이블과 `!version.txt`입니다. v0.2.9는 초기 지급 참조 검증을 위해 `Reward`, `Item`, `CardLevelRelease`, `Skill`도 포함합니다. 번들의 정규 JSON은 protobuf 필드 이름과 숫자 enum을 사용합니다.

## 근거·검증

- 실제 6.1.1의 `api/home.proto`, `api/tutorial.proto`, `api/common_response.proto`, `transaction/user.proto`, `transaction/user_tutorial.proto` descriptor로 요청·응답 필드와 변경 목록을 확인했습니다.
- iOS native `UserTutorialCollection.IsFinished`의 `0x1e0d274`에서 GameStart 완료 조건 `step > 149`를 확인했습니다. 마스터에도 마지막 체크포인트 150이 있습니다. 다른 튜토리얼을 함께 완료시키지 않습니다.
- `TimeManager.GetDeviceNowUnixTime`의 `0x1d29230`은 UTC epoch 차이에 `TimeSpan.TotalMilliseconds`를 적용합니다. 따라서 저장 시각은 Unix 밀리초입니다.
- 독립 최소 스키마와 실제 6.1.1 스키마 양쪽에서 상태 보존·설정·JST 날짜 경계·병렬 변경·오류 롤백·알 수 없는 필드 유지·실제 마스터 참조를 테스트했습니다. 외부 스키마·마스터가 없는 fresh clone에서도 최소 스키마 테스트는 실행됩니다.

일반 전투 전체, 초기 메인 지역 레슨 이외의 활동 보상, 초기 형태 범위 밖의 카드 육성, 가챠·구매 등은 범위 밖입니다. 첫 메인 라이브 실험 기능은 별도 선택 사항이며 실제 게임 재생 검증과 구분합니다. 선물 수령·친구 변경도 목록 조회와 별도 미구현입니다. 준비된 fixture도 없으면 `UNIMPLEMENTED`를 반환합니다. 현재 튜토리얼 완료 표시는 일반 전투 전체의 구현을 뜻하지 않습니다.

## 다음 구현 근거

- 공개 원본 응답 두 사례에서 카드 최고 레벨 1→2 및 41→42와 함께 `ms-normal-card_level_achievement`의 진행이 같은 값으로 갱신됩니다. 현재 `Card.Enhance`는 이 미션 delta를 누락하고, 기본 프로필에는 미션이 없으며 앱용 JSON 마스터에도 `Mission`·`Condition`이 빠져 있습니다. 개인 식별값을 제외한 [원본 근거](../tests/fixtures/official-card-level-mission.v1.json)에 고정 커밋·파일 해시·마스터 행을 보존했습니다. 이 미션 초기화·진행 보완은 아직 미구현이며 전체 미션 목록·보상 지급과 구분합니다.
- 같은 버전의 `Reward.initial_user_reward`를 신규 계정의 초기 카드·아이템 준비에 사용합니다. 공식 지급 RPC와 시점은 아직 확인하지 못했으므로 이는 로컬 생성 정책이며, 후속 선물·일반 보상 지급 계약은 별도 구현이 필요합니다.
- 서버의 자동 편성 계산·버디 대여·캐릭터 그룹 장비 제한은 추가 계약·마스터 검증이 필요합니다.
- 일반 라이브 계산에는 실제 차트·스킬·상태·확률·점수 모델이 필요합니다. 튜토리얼 두 개의 원본 기록 재생을 일반 전투 엔진으로 확장하지 않습니다.
- 모델·음성·영상은 기존 Octo 리소스 경로를 사용합니다. 홈 표시 성공 및 원본 마스터 제공과 별개로, 전체 리소스의 오프라인 보존·주소 연결은 추가 구현과 게임 기기 검증이 필요합니다.
