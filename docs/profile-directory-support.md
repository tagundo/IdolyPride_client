# 로컬 공개 프로필 조회와 초기 생일 등록

[계정·프로필·설정 API 전체 조사와 남은 미지원](account-game-api-investigation.md)에 기존 구현과 이번 두 경로를 구분했습니다.

이 문서는 새 소스의 복구 범위입니다. 배포·기기 UI 검증이 완료됐다는 뜻은 아닙니다. 공통 서버의 `Profile.FindUser`와 `Profile.UpdateBirthday`를 실제 6.1.1 protobuf 필드로 연결합니다.

## 공개 프로필 조회

선택된 로컬 계정의 저장된 `UserPublic.serverUserId` 또는 `publicUserId`를 `FindUser.userId`로 전달하면 그 계정의 저장된 이름·경험치·레벨·소속·칭호, 소개·생일·배경·레이아웃·장식·표시 선택과 좋아하는 아이돌 목록을 반환합니다. 응답의 `userId`는 저장된 서버 ID입니다. 이 두 ID를 인정하는 것은 명시적인 로컬 조회 정책이며 공식 원격 검색 규칙이 복구됐다는 주장은 아닙니다.

선택한 카드가 있으면 실제 보유 카드와 카드 이미지 마스터의 호환성을 검사해 ID·희귀도·진화·표시 선택을 반환합니다. 선택한 사진은 정확히 하나의 보유 사진에 연결되고 저장된 에셋 ID·이미지 종류가 유효해야 합니다. 없는 카드·사진을 새로 만들거나 잘못된 참조를 빈 값으로 덮지 않습니다. 사진 참조를 반환하는 것은 해당 이미지의 다운로드 완료를 뜻하지 않습니다.

등급은 기존 Home·Profile.Top과 동일하게 저장된 하이어라키 포인트와 실제 등급 마스터에서 계산합니다. 전역 순위를 계산하지 않으므로 순위는 0입니다. 다른 로컬 계정이나 원격 ID는 `NOT_FOUND`이며, 빈 사용자·친구·팔로우 관계를 생성하지 않습니다. 조회는 계정 상태를 변경하지 않습니다.

## 초기 생일 등록

`UpdateBirthdayRequest.month`·`day`는 각각 필드 1·2의 int32이며 저장 위치는 기존 `UserProfile.birthMonth`·`birthDay` 필드 5·6의 int64입니다. 월·일을 실제 달력으로 검사하며 연도를 저장하지 않는 형식이므로 2월 29일도 허용합니다.

현재 월·일이 모두 0인 계정만 처음 등록할 수 있습니다. 같은 날짜의 재요청은 현재 전체 프로필 ACK를 반환하고 원본 저장 바이트를 다시 쓰지 않습니다. 기존에 다른 날짜가 등록돼 있으면 `FAILED_PRECONDITION`으로 거절하며 자동으로 덮어쓰지 않습니다. 한쪽만 0이거나 존재하지 않는 날짜가 이미 저장된 계정도 임의 복구하지 않습니다.

등록은 SQLite 스냅샷 트랜잭션 안에서 두 필드를 함께 변경합니다. `commonResponse.updatedData.profile`에는 다른 설정과 알 수 없는 protobuf 필드를 보존한 현재 프로필을 반환합니다. 세션·다른 계정·보유 자료·미션·재화는 변경하지 않습니다.

이것은 **로컬 초기 등록 정책**입니다. 공식 서버의 연간 변경 허용 규칙이나 생일 캠페인·선물·보상을 재현하지 않습니다. 응답 스키마에 있는 `birthdayAdvInfo`와 `birthdayRemindInfo`를 근거 없이 생성하지 않으며 `Birthday.Top`·감상 완료·보상 수령 RPC는 별도 미지원 범위입니다.

## 근거와 검사

- 원본 descriptor: `data/protocol/idolypride-6.1.1.pb`, 508,520바이트, SHA-256 `c82cee62abdca7144d11e710a6f773211464a89d2ddede207999a0a5e7aec8ad`.
- `ProfileFindUserResponse`의 실제 필드 1~20과 공통 응답 9999, `FavoriteCardInfo`·`FavoritePhotoInfo`의 실제 필드를 사용합니다.
- `tests/test_profile_directory.py`는 최소 독립 스키마와 원본 6.1.1 스키마, 달력 경계·기존 생일 거절·무변경 재시도·재시작·병렬 등록/이름 변경·DB 쓰기 실패 롤백·알 수 없는 필드·다른 계정과 세션 보존, 보유 카드/사진 참조와 하이어라키, 실제 암호화 RPC 인증과 명시적 fixture 우선순위를 검사하도록 작성했습니다. 결과는 별도 실행 기록을 따릅니다.

`Auth.Create`·`Auth.Recreate`는 공식 Firebase custom token을 요구하는 계약입니다. 가짜 Firebase 토큰을 만들어 미구현을 숨기지 않습니다. `Auth.Delete` 역시 실제 계정 삭제·재가입 계약을 검증하지 않은 채 빈 성공으로 처리하지 않습니다. 이 세 호출은 기존 미지원 상태를 유지합니다.
