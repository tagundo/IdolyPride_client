# 첫 메인 영역 라이브 실험 기능

v0.3.0 베타에서 추가하고 v0.3.2에서 첫 메인 SKIP 지원을 보완한 기능이며 **기본값은 꺼짐**입니다. [v0.3.2 서버 앱](https://github.com/tagundo/IdolyPride_client/releases/tag/local-server-v0.3.2)에서 서버를 중지한 뒤 **첫 메인 라이브 실험 기능 사용**을 선택하고 시작합니다. 선택은 다음 실행에도 유지됩니다. 릴리스는 비공개 저장소의 접근 권한과 GitHub 로그인이 필요합니다. 이전 v0.2.16에는 이 기능이 없습니다.

**현재 개발 소스**는 같은 설정으로 첫 영역 `area-main-001`의 세 퀘스트를 지원하도록 확장했습니다. 기존 v0.3.2 배포본의 지원 범위는 첫 퀘스트 하나입니다. 이 확장을 포함한 앱의 배포·실제 게임 화면 검증은 별도이며, 아래 소스 지원 범위를 기존 배포 APK의 검증 결과와 구분합니다. 설정 이름과 `experimental_main_live` 불리언 API는 유지합니다.

Go SDK는 원본을 사용합니다. 이전 x86 호스트의 ARM 변환 검사에서 CPU 정보·명령 호환성 문제가 있었고, 당시 추가했던 SDK 변경은 제거했습니다. 이번 버전은 공식 ARM64 Cuttlefish/QEMU TCG에서 ARM 변환 계층 없이 검사했습니다. 이전 변환 에뮬레이터 검증 작업은 비활성 상태로 유지하며, 실제 설치 APK와 검사 도구의 소스·해시는 릴리스 기록으로 구분합니다.

개발 소스의 `/api.Quest/Start`는 `qt-main-1-001-01`, `qt-main-1-001-02`, `qt-main-1-001-03`만 지원합니다. 현재 소유 카드 다섯 장, 저장된 편성, 학습한 스킬·외형과 고정된 6.1.1 마스터로 결과를 계산합니다. 곡마다 명시적으로 고정한 실제 차트와 같은 곡의 기준 차트를 사용합니다. 계산은 출처를 보존한 Solis `live-v5`의 **로컬 규칙**이며, 공식 서버의 점수·확률과 같다는 검증은 없습니다.

v0.3.0의 Android 서버 APK는 GPU·KVM·ARM 변환 계층이 없는 공식 ARM64 Cuttlefish/QEMU TCG에서 기본 OFF·명시적 활성화, 실제 Go 계산, 첫 성공 보상과 재시도·재시작 보존을 검사했습니다. 최종 APK의 업데이트 후 세션·프로필·미션 보존도 확인했습니다. Mac은 포함된 엔진과 실제 앱 창·시작·종료 검사를 통과했습니다. 앱별 소스·검사 범위·파일 해시는 릴리스의 `RELEASE-VERIFICATION.json`과 QA ZIP에 기록했습니다. 이는 실제 게임의 일반 라이브 재생 화면을 검증한 결과와 구분합니다.

## 지원 조건

저장된 양수 `deckNumber`, `playCount=1`을 사용하며 대여 슬롯·티켓·자동 반복·포토는 지원하지 않습니다. 게임 클라이언트가 `buddyDeckName`으로 보내는 자기 덱 이름은 허용합니다. 확장된 카드 성장 형태, 지원하지 않는 스킬 해금 경계, 일치하지 않는 저장 능력치는 DB를 쓰기 전에 거부합니다. 앱에 C ABI 1 네이티브 라이브러리가 포함되어 있어야 하며, 누락·호환성 오류가 있으면 서버 시작을 중단합니다.

개발 소스는 첫 성공 보상인 `ac-1-visual-02`와 `ac-1-vocal-02`를 Part1에 장착한 덱도 준비합니다. 각각 착용 카드의 비주얼·보컬에 64를 더하며, 보유 카드의 저장 능력치나 액세서리 수량은 바꾸지 않습니다. 같은 종류를 여러 카드에 쓰려면 선택한 덱의 사용 수만큼 소유해야 합니다. 슬롯·정확한 마스터 값과 소유량을 다시 검증하고, 덱 밖의 보유 카드를 포함해 라이브 어빌리티가 초기 미학습 상태여야 합니다. Part2·다른 액세서리·퍼센트/캐릭터 보너스는 미지원입니다. **이 장비 지원은 아직 배포 APK와 실제 Auto 편성·게임 플레이에서 검증한 기능이 아닙니다.**

두 번째·세 번째 퀘스트의 시작은 같은 정산 트랜잭션 안에서 검증합니다. 앞선 모든 퀘스트의 `lastClearedTime`이 양수여야 하고, 저장 영역의 `clearQuestCount`가 실제 세 퀘스트의 성공 기록 수와 일치해야 합니다. 최고 점수나 빈 영역 행만으로 해금하지 않습니다. 첫 퀘스트의 기존 진입 동작과 이전 요청 기록 재생은 유지합니다. 두 번째 영역, 조건 평가·추가 라이브 보너스는 이 확장의 범위가 아닙니다.

**v0.3.1에서 거절하던 첫 퀘스트의 SKIP·하이라이트 시작을 v0.3.2에서 지원합니다.** 마스터의 정수 `liveSkipType=Always(2)`를 확인하고 일반 1회와 같은 실제 전체 계산·정산 경로를 사용합니다. 결과를 고정 성공 응답으로 대체하지 않으며 첫 성공 보상·경험치와 동일 요청 재시도·재시작의 보존 규칙도 같습니다. 원본 클라이언트는 정상 응답 뒤 `IsStartWithHighlight`를 설정합니다. 타입 2는 완전 생략 타입 4와 달리 라이브 장면을 불러오므로 SKIP를 켜도 장면·리소스 로딩이 완전히 생략되지는 않습니다.

개발 소스의 세 퀘스트도 각각 고정한 타입 2를 확인하며 같은 경로를 사용합니다. 자동 반복이나 완전 생략 타입 4를 허용하는 확장은 아닙니다.

네이티브 결과의 타임라인·점수·성공 여부를 응답에 담고, 현재 로컬 사용자와 저장 덱 다섯 장 및 점수 합계가 일치하는지 검증합니다. 각 퀘스트의 목표 점수로 성공 여부를 확인합니다. rank type은 `Unknown`이며 B/C/D 표시는 목표 점수의 120%/100%/0이라는 기존 **로컬 표시 정책**을 적용합니다. 첫 퀘스트는 3600/3000/0, 다음 두 퀘스트는 6480/5400/0과 12000/10000/0입니다. 순위표와 상세 분석 로그 재생은 제공하지 않습니다.

## 라이브 시작이 `UNIMPLEMENTED`로 멈출 때

v0.3.1은 실험 옵션이 켜져 있어도 SKIP 요청을 거절했습니다. 이 버전을 사용 중이면 v0.3.2 서버 앱으로 업데이트합니다.

실험 옵션의 적용 여부도 확인합니다. 기본 OFF 상태에서는 첫 메인 라이브를 실행하지 않습니다.

1. 서버 앱에서 **서버 중지**를 누릅니다.
2. **첫 메인 라이브 실험 기능 사용**을 선택하고 서버를 다시 시작합니다.
3. 시작 직후 서버 기록에 **일반 라이브 실험 기능 사용: 첫 메인 퀘스트 · 로컬 계산 규칙**이 표시되는지 확인합니다.

첫 메인 퀘스트 `qt-main-1-001-01`에서 보유 카드 다섯 장을 저장한 덱으로 1회 실행을 선택합니다. 자동 반복·티켓·포토·액세서리·대여 버디는 사용하지 않습니다. 옵션을 켠 상태와 지원 조건에서도 실패하면 진단 기록을 내보내 요청 경로와 오류를 확인합니다. v0.3.2는 `Quest.Start → UNIMPLEMENTED` 로그에 고정된 `live_rejection` 코드·한국어 사유를 추가합니다. 모드 제한으로 거절된 경우 첫 퀘스트 여부·1회 여부·자동·SKIP·티켓·버디 유무만 기록하며 계정 식별자·요청 원문·네이티브 오류 원문은 기록하지 않습니다. 다른 미지원 요청에서도 같은 상태 코드가 발생하므로 모든 오류를 OFF 설정으로 판단하지 않습니다. 점수는 계속 `live-v5` 로컬 규칙이며 실제 게임의 일반 라이브 화면 재생 검증은 남아 있습니다.

## 첫 성공 정산

개발 소스는 각 퀘스트에서 처음 성공했을 때 고정한 원본 `Quest`·`Reward` 정의의 다음 보상을 지급합니다.

| 퀘스트 끝 번호 | 목표 점수 | 강화 아이템 | 골드 / 무료 스톤 | 추가 자원 | 매니저 / 카드당 경험치 |
| --- | ---: | ---: | --- | --- | --- |
| `001-01` | 3,000 | 290 | 500 / 50 | `ac-1-visual-02` ×1 | 50 / 40 |
| `001-02` | 5,400 | 590 | 500 / 50 | `ac-1-vocal-02` ×1 | 65 / 57 |
| `001-03` | 10,000 | 890 | 500 / 50 | `item-photo_shooting-01` ×1 | 85 / 74 |

첫 영역의 보상 자원 타입은 아이템·액세서리·골드·무료 스톤으로 제한하고 해당 마스터 참조를 검증합니다. 다른 자원 타입을 액세서리로 대신 처리하지 않습니다. 지급 후 매니저 레벨과 카드 레어리티의 실제 상한을 적용합니다.

카드의 남은 경험치를 유지하고, 기존 카드 파라미터 검증기로 능력치를 갱신합니다. 강화 아이템을 소모하거나 수동 강화 시각을 바꾸지 않습니다. 응답의 보상과 전후 잔액은 현재 로컬 계정 기준입니다. 재화 상한·오버플로·잘못된 성장 상태·미지원 해금 경계가 있으면 전체 트랜잭션을 취소합니다.

첫 성공은 로컬 `UserQuest.lastClearedTime`으로 구분합니다. 새로운 요청 ID로 다시 도전하면 현재 덱으로 계산하고 최고 점수·성공 시각·횟수를 갱신하지만 **보상과 경험치를 다시 지급하지 않습니다**. 실패한 결과는 보상을 주지 않고 snapshot 바이트를 유지합니다. 팬·음악 숙련도·미션·캠페인·그 밖의 보상은 변경하지 않으며 `rewardCards.funAmount`는 0입니다. 이는 이번 실험 기능의 제한이며 원래 일반 라이브의 반복 보상 체계를 구현한 것은 아닙니다.

## 재시도와 계정 보존

`x-app-request-id`는 양수 uint64의 정규 십진수 문자열이어야 합니다. 프로필·요청 ID·요청 본문 SHA-256·RPC 경로·스키마/마스터/규칙 버전·무작위 uint64 seed·로컬 시각·전체 응답을 `main_live_attempts`에 기록합니다. 기록과 snapshot은 하나의 SQLite `BEGIN IMMEDIATE` 트랜잭션으로 저장합니다. 동시에 들어오거나 재시작 뒤 도착한 동일 요청은 계산을 다시 하지 않고 **원래 응답을 그대로 반환**합니다. 같은 ID에 다른 본문을 보내거나 저장된 스키마·마스터·규칙이 맞지 않으면 거부합니다.

일반 상태 변경은 기존 요청 기록을 보존합니다. 명시적인 snapshot 가져오기는 해당 프로필의 요청 기록과 로컬 레슨 시계만 함께 초기화하여 교체한 계정에 예전 응답을 사용하지 않게 합니다. 라이브 정산은 다른 프로필·설정·세션·레슨 시계·변경하지 않은 컬렉션과 알 수 없는 protobuf 필드를 보존합니다.

## 근거와 확인 범위

스키마와 마스터 버전은 `live_input.py`에 고정되어 있습니다. 계산기의 소스·라이선스·빌드 근거는 [네이티브 엔진 안내](../native-live-engine/README.md)에 있습니다. 요청·응답 필드는 추출한 6.1.1 descriptor, 보상·경험치는 `Quest`, `Reward`, `CardLevel`, `ManagerLevel`, `CardRarity`, `Setting` 마스터에 근거합니다. 공개 응답 참고 자료는 [sumire-sr-data c40ea107](https://github.com/Project-Hoshimi/sumire-sr-data/tree/c40ea107b9cc8e53ae1705f82a5c39cc9fe3be02/captures/2026-09-13_a12)에 고정했습니다. 같은 스테이지의 공개 기록 00019/00033은 실패 후 첫 성공을 보여 주며 이미 성공한 퀘스트의 반복 보상 근거로 사용하지 않습니다. 다른 계정의 잔액이나 상태 변경을 가져오지 않습니다.

v0.3.2의 플랫폼별 실제 실행 범위는 다음과 같습니다.

- Android: 이미 첫 퀘스트를 클리어한 계정으로 v0.3.1 SKIP 오류를 재현하고 데이터를 지우지 않은 APK 업데이트 뒤 반복 SKIP 7,174점·7,543점의 전체 타임라인·점수를 확인했습니다. 추가 보상·경험치가 없고 기존 첫 클리어를 보존했으며 동일 요청 재시도·일반/SKIP 모드 변경 충돌·SQL·세션·설정·서버 재시작을 검사했습니다. **새 계정의 첫 클리어 보상 검사는 아닙니다.**
- Linux: 실제 네이티브 엔진 검사 두 개로 새 계정의 SKIP 첫 클리어·첫 보상 1회·재시도와 계산된 0점 실패·보상 없음을 확인했습니다.
- Mac: 실제 묶음 엔진·GUI·서버 시작·종료는 일반 모드(`is_skip:false`)에서 검사했습니다. 새 SKIP 첫 클리어 실행은 검사하지 않았으며 SKIP 코드는 두 앱의 플랫폼별 핵심 모듈 40개를 빌드 소스와 대조했습니다.
